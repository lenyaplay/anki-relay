# REQ-004: Система логирования и отладочный архив

- **Статус:** done
- **Дата:** 2026-10-05
- **Связано:** ROADMAP → «Этап 4» (структурные логи); REQ-002 (нужны данные для разбора находок)

## Зачем

Когда что-то пойдёт не так у реального пользователя (синхронизация, вход, странное
поведение Claude), нужно восстановить, что происходило. Сейчас есть только stdout
контейнера: он пропадает при пересоздании контейнера и не привязан к конкретным
вызовам инструментов.

## Решения владельца

- Логи — файлы в `./logs` на хосте; плюс команда, которая собирает отладочный
  архив. Доступ только у того, кто зашёл на сервер (ssh, `docker compose exec`,
  `scp`). Ни HTTP, ни MCP логи не отдают.
- Хранение — 14 дней.
- Подробность — журнал вызовов инструментов со структурой аргументов: имена полей,
  колод, шаблонов и тегов, поисковые запросы.
- Никогда не пишутся: содержимое полей карточек, пароли, токены (OAuth, hkey, коды),
  email.

## Что меняется

1. `LOG_DIR` (по умолчанию `/logs`, пусто — только stdout) и `LOG_RETENTION_DAYS`
   (по умолчанию 14). Файл `anki-relay.log` в формате JSON Lines, ротация в полночь
   UTC, права 600.
2. Каждая запись содержит `user` (user_id) и `call_id` вызова инструмента, если
   запись сделана в его контексте (в том числе из потока синхронизации).
3. Событие `tool.call` на каждый вызов: инструмент, пользователь, длительность, исход,
   обезличенные аргументы, числовые итоги ответа.
4. События синхронизации (`sync.*`) и входа (`auth.*`) со структурированными полями.
5. Фильтр-«предохранитель», который вычищает похожие на секреты значения из любой
   записи и query string из access-логов.
6. Команда `anki-relay debug-bundle [--days N]` — архив `LOG_DIR/debug-bundle-<UTC>.tar.gz`
   с логами, версиями, обезличенной конфигурацией и состоянием синхронизации
   пользователей. Без `sync_auth.json`, `oauth.json` и коллекций.
7. Docker: том `./logs:/logs`, права для пользователя `anki`.

## Что не меняется (границы)

- Никакого HTTP- или MCP-доступа к логам.
- Формат stdout остаётся текстовым.
- Никаких внешних систем сбора логов.

## Влияние на синхронизацию и данные пользователей

На синхронизацию не влияет. Риск — утечка личных данных в логи; закрывается
обезличиванием аргументов, фильтром-предохранителем и тестом, который проверяет
лог-файл после полного OAuth-входа и серии вызовов.

## Отклонения и заметки по реализации

1. Аргументы инструментов пишутся в поле `arguments`: имя `args` зарезервировано в
   `logging.LogRecord`. Первая версия падала на каждом вызове; поймано тестами
   `test_tools.py`.
2. `uvicorn.run(log_config=None)`: иначе uvicorn вешает на свои логгеры собственные
   обработчики с `propagate=False`, и access-логи не попадают в файл.
3. Отложенная отправка планируется в пустом `contextvars.Context()`: иначе push
   наследовал бы `call_id` вызова, который первым его запустил, и вводил бы в
   заблуждение при разборе.
4. По итогам ручного просмотра лога контейнера:
   - из JSON убрано служебное поле uvicorn `color_message`;
   - успешные `GET /health` от healthcheck Docker не логируются (~2900 строк в
     день шума). Неуспешные пишутся.
5. Архив создаётся внутри `LOG_DIR`. Если команда запущена от root через
   `docker compose exec`, владелец файла меняется на владельца папки. Забирать архив
   удобнее через `docker compose cp` — тогда не нужен `sudo` на хосте.
6. `LOG_DIR` в `docker-compose.yml` задан как `${LOG_DIR-/logs}`, поэтому
   `LOG_DIR=` (пусто) в `.env` действительно отключает файловые логи.
