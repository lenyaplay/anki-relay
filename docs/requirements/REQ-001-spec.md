# Промпт: Anki Relay, MCP-коннектор Anki для Claude

Создай с нуля проект **Anki Relay** (репозиторий и Docker-сервис `anki-relay`, Python-пакет `anki_relay`). Это self-hosted MCP-сервер, который подключается к Claude (claude.ai, десктоп, мобильные приложения) как кастомный коннектор и даёт Claude работать с коллекциями Anki нескольких доверенных пользователей. Проект пойдёт в публичный репозиторий на GitHub, поэтому нужен чистый код, тесты, документация и никаких секретов в репозитории.

## Как это работает

```
Claude → https://anki-relay.example.com/mcp (OAuth) → MCP-сервер + копии коллекций пользователей ⇄ AnkiWeb ⇄ устройства пользователей
```

- Сервер ведёт себя как ещё одно устройство Anki. Для каждого пользователя он хранит на диске свою копию коллекции (`collection.anki2` и папку медиа) и синхронизирует её с AnkiWeb через официальную Python-библиотеку `anki` (тот же движок, что в Anki Desktop). AnkiConnect и запущенный Anki Desktop не нужны.
- Карточки, созданные Claude, попадают на телефон и компьютер пользователя через обычную синхронизацию Anki.
- Войти могут только email-адреса из списка `ALLOWED_EMAILS`. У каждого пользователя своя коллекция, свой токен AnkiWeb и свои OAuth-токены, и доступа к чужим данным у него нет.

## Стек и версии

- Python 3.12, библиотека `anki` (зафиксировать точную версию, актуальную на момент работы), MCP Python SDK **1.x**: `mcp>=1.10,<2`. В `mcp` 2.x класс `FastMCP` переименован, и API изменилось, поэтому держимся 1.x. HTTP-клиент для скачивания медиа: `httpx`.
- Транспорт: Streamable HTTP на пути `/mcp`, `stateless_http=True`.
- **Не полагайся на память об API `anki` и `mcp`.** Поставь пакеты и проверь сигнатуры через `inspect` до того, как писать код. Ниже перечислены места, где легко ошибиться.
- `import anki.collection` должен выполняться до `from anki.notes import ...`, иначе будет циклический импорт.

## Инструменты MCP

### Принцип

Сервер — **тонкая универсальная обёртка над возможностями Anki**, без собственных абстракций, пресетов и «правильных» структур. Никаких встроенных типов заметок, шаблонов, схем тегов или сценариев. Claude должен уметь всё, что умеет пользователь в Anki Desktop при работе со структурой коллекции: изучить, что есть, спроектировать новое, перестроить существующее и наполнить его. Инструменты называются и устроены в терминах Anki (deck, note type, field, template, card, tag, deck options, search query).

Все инструменты работают с коллекцией **текущего пользователя**. Пользователь определяется по OAuth-токену запроса: `get_access_token()` из `mcp.server.auth.middleware.auth_context`, поле `subject`. Проверь, что контекст корректно доступен в stateless-режиме.

### Набор инструментов

Все пакетные инструменты принимают списки и возвращают результат по каждому элементу (успех или причина ошибки), а не падают на первой ошибке. Списочные инструменты поддерживают `limit` и `offset`.

### Общие требования к инструментам

- Опасные инструменты (удаление, сброс, изменение схемы) в описании содержат «покажи пользователю, что будет затронуто, и получи подтверждение перед вызовом». Кроме того, у них есть параметр `dry_run` (по умолчанию `true`): вызов без `dry_run=false` ничего не меняет и возвращает, сколько заметок, карточек и колод будет затронуто.
- В `instructions` сервера кратко: «изучай структуру через `collection_overview` и `get_note_type` перед изменениями; поля принимают HTML; для медиа сначала вызови `add_media`; добавляй заметки пакетами; проверяй шаблоны через `preview_card`; перед опасными операциями делай `dry_run`».
- `add_notes` проверяет каждую заметку через `note.fields_check()` и пропускает пустые, дубликаты (если не `allow_duplicates`) и некорректный cloze. Сравнивать нужно с enum `NoteFieldsCheckResult` (`EMPTY`, `DUPLICATE`, `MISSING_CLOZE`, `NOTETYPE_NOT_CLOZE`, `FIELD_NOT_CLOZE`), а не с числами.
- Неизвестное имя поля, типа, колоды или шаблона даёт понятную ошибку со списком допустимых вариантов.
- Ответы компактные: без лишних полей и без HTML-шума, где он не нужен, чтобы большие коллекции не съедали контекст Claude.
- Любой инструмент можно отключить настройкой `DISABLED_TOOLS` (список имён через запятую); отключённые инструменты не регистрируются вовсе. По умолчанию включены все.
- Используй публичные методы `anki` (`col.models`, `col.decks`, `col.sched`, `col.tags`, `col.media`, `col.card_stats` и т. п.), а не прямой SQL. Перед реализацией проверь реальные сигнатуры.

### `add_media`: возможности и настройки

Принцип: по умолчанию разрешено всё, что поддерживает Anki. Защита остаётся включённой только там, где она ничего не отнимает при обычном использовании, и каждую можно выключить.

- Ровно один источник: `url` или `data_base64`.
- Разрешённые расширения — `MEDIA_ALLOWED_EXTENSIONS`. По умолчанию это всё, что Anki умеет показывать или проигрывать: картинки (`png jpg jpeg gif webp svg avif bmp tif tiff ico`), аудио (`mp3 ogg oga opus wav flac m4a aac`) и видео (`mp4 webm mkv mov`). Значение `*` разрешает любые файлы.
- SVG не санируется. Поля заметок и так принимают произвольный HTML, так что отдельная санация SVG ничего не даёт; это нужно пояснить в README.
- Лимит размера — `MEDIA_MAX_MB`, по умолчанию 100. Размер проверяется потоково, без загрузки всего файла в память.
- Скачивание по URL:
  - только `http` и `https`, не больше 5 редиректов, таймаут `MEDIA_DOWNLOAD_TIMEOUT` (по умолчанию 60 секунд);
  - защита от SSRF включена по умолчанию: DNS разрешается заранее, приватные, loopback, link-local и metadata-адреса (`169.254.169.254` и т. п.) запрещены, проверка повторяется на каждом редиректе. Выключается через `MEDIA_ALLOW_PRIVATE_URLS=true` — для тех, кто хочет брать файлы с NAS или других сервисов в своей сети. В README объяснить, чем это грозит;
  - если сервер вернул `Content-Type`, а в имени файла нет расширения, расширение подставляется по типу.
- Имя файла санируется (никаких `/`, `..`, управляющих символов). Файл записывается через `col.media.write_data()`, которая сама разрулит совпадения имён. Вернуть нужно то имя, которое она дала.
- Ответ инструмента содержит готовую вставку: `<img src="...">` для картинок, `[sound:...]` для аудио и видео.

## Синхронизация (самое важное, данные пользователей бесценны)

### Коллекция: когда синхронизироваться

Ведём себя как обычный клиент Anki, без лишних запросов к AnkiWeb (типичная нагрузка: 20–60 заметок за полчаса серией вызовов).

- **Подтягивание.** Перед инструментом, который читает или меняет заметки, карточки, колоды или теги, выполняется `sync_collection(auth, sync_media=False)`, но только если последняя успешная синхронизация была раньше, чем `SYNC_PULL_INTERVAL` секунд назад (по умолчанию 60). Серия вызовов от Claude даёт одну синхронизацию, а не по одной на вызов.
- **Отправка.** После изменения коллекция помечается как изменённая, и запускается таймер. Через `SYNC_PUSH_DELAY` секунд без новых изменений (по умолчанию 10) выполняется одна синхронизация на всю серию. Каждое новое изменение перезапускает таймер, но не дольше `SYNC_PUSH_MAX_DELAY` (по умолчанию 60) с первого несинхронизированного изменения.
- При корректной остановке сервера (SIGTERM) неотправленные изменения синхронизируются. При старте сервер проверяет пометку «есть неотправленное» в `state.json` и синхронизирует.
- `sync()` синхронизирует немедленно, без учёта интервалов.
- Ошибки сети и ответы AnkiWeb об ограничении частоты: повтор с экспоненциальной паузой (до нескольких минут), без шквала запросов. Состояние видно в `sync_status()`.

### Коллекция: обработка `SyncOutput.ChangesRequired`

- `NO_CHANGES` и `NORMAL_SYNC` — всё в порядке.
- `FULL_DOWNLOAD`, а также `FULL_SYNC`, если копия пользователя ещё ни разу не синхронизировалась (флаг в его `state.json`), — выполнить полное скачивание: `close_for_full_sync()` → `full_upload_or_download(upload=False)` → `reopen(after_full_sync=True)`.
- `FULL_UPLOAD` и `FULL_SYNC` в любой другой ситуации — **ничего не делать** и вернуть ошибку с подсказкой: «синхронизируйте Anki на компьютере, затем вызовите `sync(force_download=true)`».
- Если пришёл `new_endpoint`, сохранить его.

### Изменения схемы и полная выгрузка

Изменение схемы (поля и шаблоны карточек существующего типа, удаление типа, `change_note_type`) Anki не может передать обычной синхронизацией. После него нужна односторонняя полная выгрузка коллекции на AnkiWeb: так же делает Anki Desktop, предупреждая «это потребует односторонней синхронизации». Без этой возможности Claude не сможет перестраивать структуру, поэтому полная выгрузка разрешена **только** по такому протоколу:

1. Инструмент, меняющий схему, вызывается с `dry_run=true` (по умолчанию). Он возвращает, что изменится, и предупреждение для пользователя: «перед подтверждением синхронизируйте все устройства; после изменения на каждом устройстве нужно будет выбрать “Скачать с AnkiWeb”, несинхронизированные повторения на них пропадут».
2. При `dry_run=false` сервер **сначала** делает обычную синхронизацию, и она обязана завершиться с `NO_CHANGES` или `NORMAL_SYNC`. Если она требует полной синхронизации или упала с ошибкой, операция отменяется.
3. Сервер делает резервную копию файла коллекции пользователя (`data/users/<id>/backups/`, хранятся последние `BACKUP_KEEP`, по умолчанию 10).
4. Выполняется изменение схемы, и сразу за ним — полная выгрузка: `close_for_full_sync()` → `full_upload_or_download(upload=True)` → `reopen(after_full_sync=True)`.
5. Если выгрузка не удалась, в `state.json` ставится пометка «незавершённая смена схемы». Пока она стоит, обычная синхронизация не выполняется (иначе можно потерять изменение), а `sync_status` и все инструменты сообщают об этом. Повторить выгрузку можно через `sync()`.

Никаких других путей к `upload=True` в коде быть не должно; это нужно покрыть тестом. Выключатель `ALLOW_SCHEMA_CHANGES` (по умолчанию `true`): при `false` все меняющие схему инструменты не регистрируются, и сервер не выполняет полную выгрузку никогда.

Проверь по коду `anki`, какие именно операции помечают схему изменённой (как правило, это делается через `col.mod_schema`, проверь). Создание нового типа, CSS и тексты шаблонов схему, как правило, **не** меняют. Список «меняет схему» в инструментах должен соответствовать реальности, и это нужно проверить тестом: после операции следующая синхронизация не требует полной.

### Медиа

- Медиа синхронизируются отдельным протоколом: `col.sync_media(auth)`. Он запускается в фоне внутри бэкенда, статус доступен через `col.media_sync_status()`; проверь точные API.
- Медиасинхронизация запускается вместе с отложенной отправкой изменений и при `sync()`. Инструмент ждёт её завершения до 30 секунд, после этого возвращает «медиа досинхронизируются в фоне». Нельзя запускать вторую медиасинхронизацию, пока идёт первая.
- Настройка `MEDIA_SYNC`, по умолчанию `true`. В README предупредить: медиасинхронизация двусторонняя, поэтому при первом запуске на сервер скачиваются **все** медиафайлы пользователя, а это может занять гигабайты. При `false` инструмент `add_media` отключён.

### Потоки и память

- Коллекция Anki не потокобезопасна: у каждого пользователя свой `threading.Lock`, весь доступ к его коллекции идёт через этот лок. Блокирующие вызовы из async-кода выполняются через `asyncio.to_thread`.
- Коллекции открываются лениво и закрываются после `COLLECTION_IDLE_MINUTES` простоя.

## Авторизация: OAuth 2.1 со входом через AnkiWeb

Кастомные коннекторы Claude поддерживают OAuth с динамической регистрацией клиентов (DCR). Пользователь вставляет в Claude адрес `https://<хост>/mcp`, нажимает Connect, видит страницу входа нашего сервера и вводит **email и пароль от AnkiWeb**.

### Реализация

- Реализовать `OAuthAuthorizationServerProvider` из `mcp.server.auth.provider` и передать его в `FastMCP(auth_server_provider=..., auth=AuthSettings(...))`. В настройках: `issuer_url=PUBLIC_URL`, `resource_server_url=PUBLIC_URL + "/mcp"`, `validate_token_resource=False` (иначе будет DeprecationWarning), DCR и revocation включены.
- `authorize()` перенаправляет на нашу страницу `/login?req=<id>` (через `@mcp.custom_route("/login", methods=["GET","POST"])`). Запрос на вход живёт 10 минут и одноразовый.

### Проверка при входе (POST)

1. Email приводится к нижнему регистру и должен входить в `ALLOWED_EMAILS`. Если нет — отказ, и **AnkiWeb при этом не вызывается**.
2. Учётные данные проверяются у AnkiWeb через `col.sync_login(username, password, endpoint=None)` в отдельном потоке. Неверный пароль приходит как `anki.errors.SyncError` с полем `.kind` (enum `SyncErrorKind`; проверь точное имя значения для ошибки авторизации). Сообщения для пользователя: «неверный email или пароль», «AnkiWeb не ответил», «нет связи с AnkiWeb».
3. При успехе в папку пользователя сохраняются **только** `hkey` и `endpoint` (`sync_auth.json`, права 600). **Пароль никуда не записывается и не логируется.**

### Пользователи

- `user_id` = первые 16 hex-символов sha256 от email в нижнем регистре. Данные лежат в `data/users/<user_id>/`: коллекция, медиа, `sync_auth.json`, `state.json`.
- `user_id` записывается в `subject` кодов, access- и refresh-токенов.
- При каждой проверке токена сервер убеждается, что email владельца всё ещё в `ALLOWED_EMAILS`. Если адрес убрали из списка и перезапустили сервер, доступ пропадает сразу, даже с живыми токенами. Для этого в `oauth.json` хранить соответствие `user_id` → email.

### Токены и хранение

- Access-токен живёт `ACCESS_TOKEN_TTL`, refresh — `REFRESH_TOKEN_TTL_DAYS` с ротацией при каждом обновлении (старый refresh перестаёт работать). Код авторизации одноразовый и живёт 5 минут, PKCE проверяет SDK. Все токены генерируются через `secrets.token_urlsafe(32)`.
- Клиенты и токены хранятся в `data/oauth.json` (атомарная запись через временный файл, права 600, просроченные записи чистятся), чтобы перезапуск не разлогинивал пользователей.
- Защита от перебора: после `LOGIN_MAX_FAILS` неудачных попыток за `LOGIN_FAIL_WINDOW` с одного IP вход для этого IP блокируется, плюс общий лимит в 5 раз больше. На каждую неудачу задержка 1 секунда через `asyncio.sleep`, не `time.sleep`. Настоящий IP клиента брать из `X-Forwarded-For` только если запрос пришёл от доверенного прокси (`TRUSTED_PROXIES`, по умолчанию адреса Docker-сети и `127.0.0.1`).

### Страница входа

- Два языка, русский и английский. Язык по умолчанию — `DEFAULT_LANGUAGE`; при `auto` берётся из `Accept-Language`, переключатель RU / EN наверху страницы сохраняет выбор в cookie `lang` и не теряет `req`. Все тексты, включая ошибки, лежат в одном словаре переводов.
- Без внешних ресурсов, адаптивная вёрстка, светлая и тёмная тема через `prefers-color-scheme`. Все подставляемые значения экранируются через `html.escape`.
- Подпись под формой: «Войдите аккаунтом AnkiWeb. Пароль проверяется у AnkiWeb и на сервере не сохраняется.» / «Sign in with your AnkiWeb account. Your password is checked by AnkiWeb and never stored on this server.»

### Транспортная безопасность

- `TransportSecuritySettings`: защита от DNS rebinding включена, `allowed_hosts` берутся из хоста в `PUBLIC_URL`, `allowed_origins=["https://claude.ai", "https://claude.com"]`.
- Callback Claude: `https://claude.ai/api/mcp/auth_callback`. Его нужно использовать в тестах.

```
PUBLIC_URL=https://anki-relay.example.com   # обязательно: внешний адрес сервера, без /mcp
```

Всё остальное необязательно, у каждой настройки есть значение по умолчанию. Принцип: **по умолчанию включены все возможности**, а настройки позволяют их урезать или ослабить защиту.

|---|---|---|

| `MEDIA_MAX_MB` | `100` | Лимит размера одного файла |

| `MEDIA_ALLOW_PRIVATE_URLS` | `false` | Разрешить скачивание с адресов внутренней сети |
| `SYNC_PULL_INTERVAL` | `60` | Не подтягивать изменения с AnkiWeb чаще, чем раз в столько секунд |
| `SYNC_PUSH_DELAY` | `10` | Через сколько секунд тишины отправлять накопленные изменения |
| `SYNC_PUSH_MAX_DELAY` | `60` | Максимальная задержка отправки при непрерывной серии изменений |

| `LOGIN_MAX_FAILS` | `10` | Неудачных попыток входа с одного IP за `LOGIN_FAIL_WINDOW` до блокировки |
| `LOGIN_FAIL_WINDOW` | `900` | Окно подсчёта неудачных попыток, в секундах |
| `COLLECTION_IDLE_MINUTES` | `30` | Через сколько минут простоя закрывать коллекцию в памяти |
| `DEFAULT_LANGUAGE` | `auto` | Язык страницы входа: `auto` (по браузеру), `ru` или `en` |
| `TRUSTED_PROXIES` | Docker-сеть и `127.0.0.1` | Каким прокси доверять заголовок `X-Forwarded-For` |

- Без `PUBLIC_URL` или с пустым `ALLOWED_EMAILS` сервер не стартует и выводит понятное сообщение.
- `PUBLIC_URL` должен начинаться с `https://`. Исключение — `http://localhost` и `http://127.0.0.1` для разработки и тестов.

## Два режима развёртывания

### 1. Всё из коробки (по умолчанию)

`COMPOSE_PROFILES=caddy` → `docker compose up -d` поднимает приложение и Caddy. Caddy сам получает сертификат Let's Encrypt для хоста из `PUBLIC_URL` и проксирует запросы на приложение. Порты 80 и 443 должны быть открыты.

### 2. Свой nginx

`COMPOSE_PROFILES=` (пусто) → поднимается только приложение, оно опубликовано на `${BIND_ADDRESS}:${APP_PORT}` (по умолчанию `127.0.0.1:8000`). HTTPS и проксирование делает nginx пользователя. В репозитории лежит готовый `deploy/nginx.conf.example`, который в комментариях объясняет каждую нужную директиву:
- `proxy_pass http://127.0.0.1:8000;` (с комментарием: порт должен совпадать с `APP_PORT`);
- `proxy_set_header Host $host;` — нужен для проверки хоста;
- `X-Forwarded-For` и `X-Forwarded-Proto`;
- `proxy_http_version 1.1; proxy_buffering off; proxy_read_timeout 300s;` — без этого ломаются потоковые ответы MCP;
- `client_max_body_size` не меньше лимита медиа с запасом на base64.

### Docker Compose

- Все порты и адреса в `docker-compose.yml` берутся из `.env` с значениями по умолчанию, ничего не захардкожено:
  - `anki-relay`: `"${BIND_ADDRESS:-127.0.0.1}:${APP_PORT:-8000}:${PORT:-8000}"`;
  - `caddy`: `"${HTTP_PORT:-80}:80"`, `"${HTTPS_PORT:-443}:443"` и `"${HTTPS_PORT:-443}:443/udp"` (HTTP/3).
- Caddy обращается к приложению по внутренней Docker-сети (`anki-relay:${PORT}`), поэтому в режиме `caddy` порт приложения на хосте вообще не нужен. Значение по умолчанию `127.0.0.1` гарантирует, что он не торчит наружу.
- Если `BIND_ADDRESS=0.0.0.0`, приложение доступно по чистому HTTP напрямую. В README предупредить, что тогда порт нужно закрыть файрволом, а в `TRUSTED_PROXIES` указать адрес прокси.
- При нестандартных `HTTP_PORT` и `HTTPS_PORT` Let's Encrypt не сможет выпустить сертификат обычным способом. В README это нужно объяснить и показать, когда такие порты имеют смысл (например, если перед Caddy стоит ещё один прокси или используется DNS-challenge).
- Сервис `caddy` имеет `profiles: ["caddy"]`.
- Caddyfile берёт хост из переменной: передать в Caddy `SITE_ADDRESS`, вычисленный из `PUBLIC_URL`, или просто требовать в `.env` `PUBLIC_URL` и разбирать его в Caddyfile. Выбери надёжный способ и задокументируй его.

Сеть и настоящий AnkiWeb в тестах не используются: проверка входа, синхронизация коллекции, синхронизация медиа и HTTP-скачивание подменяются.

**`test_tools.py`:**
- каждый инструмент из списка вызывается хотя бы раз на временной коллекции;

- вызов через настоящий MCP-клиент (`mcp.client.streamable_http`) на запущенном сервере.

**`test_note_types.py`:**

**`test_sync.py`** (AnkiWeb подменён фейком, который считает вызовы):
- серия из 20 вызовов за несколько секунд даёт одно подтягивание и одну отправку;

- обычный путь никогда не вызывает `upload=True`; полная выгрузка возможна только из протокола смены схемы;

- перед выгрузкой создаётся резервная копия, а старые копии сверх `BACKUP_KEEP` удаляются;
- неудачная выгрузка ставит пометку «незавершённая смена схемы», которая блокирует обычную синхронизацию;

## Порядок работы

1. Установи зависимости и проверь реальные API `anki` и `mcp` через `inspect`: синхронизацию коллекции и медиа, `SyncError`, менеджер медиа, контекст токена.
2. Напиши код, затем тесты, и прогони тесты и `ruff` до зелёного состояния.
3. Собери Docker-образ и проверь оба режима compose: с профилем `caddy` и без него. Проверь, что смена `APP_PORT` и `BIND_ADDRESS` в `.env` действительно меняет публикацию порта (`docker compose config`). Без обязательных переменных контейнер должен падать с понятной ошибкой.
4. Убедись, что в репозиторий не попали `.env`, `data/` и любые токены.
5. В конце коротко отчитайся: что сделано, как запустить, и что не проверено (настоящая синхронизация с AnkiWeb требует реального аккаунта).
