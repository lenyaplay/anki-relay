# REQ-003: Решения при требовании полной синхронизации

- **Статус:** done
- **Дата:** 2026-10-05
- **Связано:** ROADMAP → «Этап 3»; находка №1 в REQ-001

## Зачем

Интеграционный тест на настоящем `anki.syncserver` показал: после того как другое
устройство меняет структуру типа заметок и выгружает коллекцию, сервер получает
`FULL_SYNC`. По REQ-001 это всегда ошибка с просьбой вызвать
`sync(force_download=true)`, хотя часто скачивание ничего не теряет: копия сервера —
реплика, и если на ней нет неотправленного, всё её содержимое уже есть в AnkiWeb.
Это частый случай (любая правка структуры в Anki Desktop), и лишний круг через
Claude и пользователя только мешает. В остальных случаях Claude должен решать
вместе с пользователем, и для этого ему нужно структурированное состояние, а не
только текст.

## Что меняется

1. Полное скачивание выполняется автоматически, если копия сервера «чистая»:
   ответ `FULL_SYNC` или `FULL_DOWNLOAD`, нет неотправленных изменений
   (`dirty=false`) и локальная схема не менялась (`schema_changed()=false`).
   Перед скачиванием, как и раньше, делается резервная копия; инструмент получает
   предупреждение.
2. Если скачивание небезопасно, ошибка содержит структурированный блок `full_sync`:
   `answer`, `unsynced_changes_on_server`, `local_schema_changed`,
   `pending_schema_upload`, `ankiweb_empty`, `safe_to_download`,
   `backup_on_download`. Тот же блок показывает `sync_status`, пока конфликт не
   разрешён.
3. `FULL_UPLOAD` (коллекция в AnkiWeb пустая) никогда не обрабатывается
   автоматически. Сообщение предлагает выяснить у пользователя, был ли сброс
   намеренным.
4. В инструкциях сервера: при `safe_to_download=false` пересказать пользователю,
   что будет потеряно, и вызывать `force_download` только после его подтверждения.

## Что не меняется (границы)

- Выгрузка (`upload=True`) возможна по-прежнему только в протоколе смены схемы.
- Отправка изменений и предварительная синхронизация протокола схемы никогда не
  скачивают коллекцию сами (`allow_full_download=False`).
- `sync(force_download=true)` работает как раньше.

## Влияние на синхронизацию и данные пользователей

Скачивание меняет только копию сервера; AnkiWeb и другие устройства не
затрагиваются. Потерять можно только то, что есть на сервере и чего нет в AnkiWeb:
неотправленные правки, неотправленную смену схемы или (при пустом AnkiWeb) всю
копию. Все три случая исключены условием автоматического скачивания. Резервная копия
делается всегда.

- [x] AC2 Неотправленные изменения + `FULL_SYNC` → ошибка с `safe_to_download=false`; блок есть и в `sync_status`; скачивания нет (`test_sync.py`, интеграционный тест).
- [x] AC3 `FULL_UPLOAD` → ошибка с `ankiweb_empty=true`; ни скачивания, ни выгрузки (`test_sync.py`).

## Отклонения и заметки по реализации

1. Для ещё ни разу не синхронизированной копии `dirty` и `schema_changed()` не
   учитываются: свежая коллекция всегда числится «с изменённой схемой» (`ls=0`), а
   инструменты до первой синхронизации не работают, так что неотправленного там быть
   не может.
2. Отложенная отправка и предварительная синхронизация протокола схемы по-прежнему
   вызываются с `allow_full_download=False`. Отправка запускается только при
   неотправленных изменениях, поэтому `safe_to_download` для неё всегда `false`.
3. Блок `full_sync` дописывается к тексту ошибки строкой
   `full_sync: {...}` (компактный JSON): у `ToolError` в MCP есть только текст.
4. REQ-005 заменил поле `ankiweb_empty` (вывод из ответа) фактическим
   `download_offered` и убрал из текстов предположения о причинах.
5. Интеграционный тест на настоящем `anki.syncserver` проверяет обе ветки:
   автоскачивание после смены схемы на «десктопе» и ошибку при неотправленных
   изменениях.
